# Continually Self-Evolving DeepSeek Harness 决策记录

> 建立日期：2026-08-17  
> 用途：记录项目负责人已经明确确认的决定，防止后续设计和实现过程中发生无意识漂移。  
> 维护方式：只在文档末尾追加。已有决定发生变化时，不删除或改写旧决定，而是新增一条决定并注明它取代了哪一条。

## 使用规则

1. 只有经过项目负责人明确确认的内容才能记为“已确认”。
2. 讨论中的建议不能冒充决定，应记录在“待确认问题”中。
3. 每条决定至少写明：决定、原因、对实现的约束。
4. 新决定与旧决定冲突时，以日期更晚且明确写有“取代”的决定为准。
5. 后续对话中形成新共识时，在本文末尾继续追加。

## 2026-08-17：初始蓝图与第一期原则

### D-001：项目首先是研究型原型

**状态：已确认**

未来 12～18 个月，项目首先要证明：长期真实经验能否产生可验证、可保留、可撤销的 Harness 改进。

项目可以在研究成功后发展成个人或小团队长期使用的内部系统，但第一阶段不以商业化产品为目标。

**对实现的约束：**

- 不因未来商业化的可能性提前建设多用户、租户隔离、完整权限体系和产品界面；
- 第一优先级是研究闭环的真实性，而不是功能数量和使用体验；
- 如果不能从真实经验中产生有效改进，不用更多平台功能掩盖核心假设未被证明的问题。

### D-002：人在第一期是审查者，不是幕后问题发现者

**状态：已确认**

系统必须主动从长期任务记录中发现重复问题。人可以：

- 确认问题是否真实、是否属于 Harness；
- 修正事故测试中的明显错误；
- 审查候选插件；
- 批准正式启用或执行恢复。

人不能先把真实问题和解决方法完整告诉系统，再把结果当成自主发现成果。

**对实现的约束：**

- 真实研究结果必须保留系统主动发现问题的证据；
- 人工干预必须记录，不能隐藏；
- 人工准备的练习题不能计入自主发现成果。

### D-003：第一期以真实代码任务为主要实验场景

**状态：已确认**

第一期主要从真实代码开发任务中积累经验。代码任务容易使用 Git、文件快照和测试验证修改效果，但研究对象不限于简单工具报错。

值得关注的问题包括但不限于：

- 没有验证就宣布完成；
- 只修表面症状，没有追踪共同原因；
- 反复尝试同一种无效方案；
- 长任务中遗忘关键要求；
- 工具结果已经否定假设，仍沿错误方向继续；
- 修改范围失控；
- 没有保护用户已有改动；
- 失败后没有正确恢复或向用户说明。

**对实现的约束：**

- 简单工具错误可以用于打通工程流程，但不能成为唯一研究目标；
- 第一阶段的经验提取和测试机制要能够逐步覆盖更有意义的代码任务弱点；
- 是否属于 Harness 问题必须允许回答“不确定”或“不是”。

### D-004：采用练习题和真实任务分开的双轨验证

**状态：已确认**

第一期同时使用两套严格分开的任务材料：

1. 人工准备的已知失败案例，用来检查采集、测试、修改、版本和恢复流程能否运行；
2. 未提前告知问题的真实代码任务，用来证明系统能否自主发现 Harness 弱点。

**对实现的约束：**

- 两套材料分开标记、分开统计；
- 人工练习题只能证明工程管道可用，不能算作自主发现成果；
- 第一阶段最终研究里程碑必须包含至少一个来自未干预真实任务的问题。

### D-005：第一期固定主要实验基线

**状态：已确认**

第一期使用固定的 DeepSeek Harness 版本、模型、主要配置和模型参数作为实验基线。

**对实现的约束：**

- 每个候选记录它所依赖的 Harness、模型和配置版本；
- 实验期间如果外部版本变化，尚未完成验证的候选需要重新建立基线；
- 不能把模型升级、配置变化或官方 Harness 更新带来的改善归功于自进化插件。

### D-006：事故测试必须先于候选修改冻结

**状态：已确认**

采用测试先行顺序：

```text
真实事故
→ 生成并冻结测试
→ 确认旧版本失败
→ 生成候选插件
→ 确认新版本通过
```

对于无法完整恢复的环境，优先保存重现问题所需的最小信息，例如关键工具输入和返回结果，并把它做成事故测试。不为第一期建设能够恢复所有外部世界状态的通用平台。

**对实现的约束：**

- 生成候选以后不能悄悄修改测试来配合答案；
- 无法形成可信测试时允许标记为“暂时无法验证”；
- 只通过智能体自评不能正式保留候选。

### D-007：候选正式保留必须通过独立的相似测试

**状态：已确认**

候选插件正式保留前，至少需要：

1. 冻结的真实事故测试中，旧版本失败、新版本通过；
2. 至少一个未参与生成修改、内容不同但机制相同的测试通过；
3. 一小组原本正常的代码任务没有明显退化；
4. 人工确认候选没有写死答案。

**对实现的约束：**

- 候选不能只凭自己的事故测试正式启用；
- 独立相似测试在候选生成前准备，并且不提前暴露给候选生成步骤；
- 样本不足时结论是“证据不足”，而不是降低标准。

### D-008：第一期允许充分使用 Cordis 创造模式

**状态：已确认**

第一期不把候选限制成“修改提示词”或“一条工具规则”。系统可以使用 DeepSeek Harness 已有的 Cordis 创造模式生成完整动态插件，包括：

- 注册新工具；
- 监听并干预运行事件；
- 包装工具执行流程；
- 检查智能体是否可以结束；
- 提供新的内部能力；
- 增加提示内容；
- 必要时增加简单界面；
- 为解决同一个问题组合多个相关动作。

第一期的限制按照风险、权限和问题范围制定，而不是按照功能种类制定。

**对实现的约束：**

- 一个候选只解决一个明确问题，但可以在一个插件中组合解决该问题所必需的多个动作；
- 候选必须使用已经检查过的公开 Cordis 能力；
- 第一阶段不修改 DeepSeek Harness 核心源码；
- 不修改权限、安全隔离、密钥、模型和实验评判标准；
- 不绕过用户批准；
- 不在真实环境执行不可恢复的外部操作；
- 候选必须隔离测试并由人批准正式启用。

### D-009：动态创造用于试验，批准后转为磁盘上的正式插件

**状态：已确认**

Cordis 动态插件只作为候选试验形式。候选通过测试并获得批准后，转成磁盘上的正式 Cordis 插件，通过 DeepSeek Harness 正常配置加载。

正式保存的材料至少包括：

- 插件代码；
- 它解决的问题；
- 原始事故证据；
- 冻结测试和独立相似测试；
- 测试结果；
- 所依赖的 Harness、模型和配置版本；
- 上一个正式版本。

**对实现的约束：**

- 不把进程内动态插件登记表当作长期版本库；
- 重启后由正式配置恢复已经批准的插件；
- 恢复旧版本通过重新加载上一个磁盘版本完成；
- 第一版只需要当前正式版本、上一个正式版本和一个候选版本。

### D-010：长期采用分级自主，而不是完全自动或永远人工

**状态：已确认**

长期方向是按风险逐步开放自主能力：

- 提示内容、只读检查和辅助界面等低风险插件，在积累足够安全记录后可以自动正式启用；
- 会改变执行流程、调用工具或写文件的插件继续需要人工批准；
- 权限、安全、密钥、外部系统写入和核心运行流程永远不自动修改或启用。

**对实现的约束：**

- 第一期所有正式启用都需要人工批准；
- 自动化权限只能根据真实安全记录逐类开放；
- 不能因为某项自动启用能力已经实现，就默认对所有候选开放。

### D-011：第一期不建设多智能体团队

**状态：已确认**

第一期使用同一个固定模型，但把关键工作分成相互隔离的三个步骤：

1. 分析步骤：从真实记录中提出问题；
2. 测试步骤：根据事故生成并冻结测试；
3. 修改步骤：根据问题和公开测试生成插件。

至少保留一个候选生成步骤不可见的独立相似测试。

**对实现的约束：**

- 不建设分析员、研究员、开发员、评审员互相讨论的多智能体组织；
- 三个步骤的输入和可见信息要明确分开；
- 测试冻结后，修改步骤不能反向改写它；
- 独立相似测试的结果由验证流程产生，不由候选自评。

### D-012：项目按四期推进

**状态：已确认**

项目总体按照以下顺序推进：

1. 第一期：证明一次真实的最小闭环；
2. 第二期：证明可以持续产生多个有效改进；
3. 第三期：在风险控制下实现可靠的半自动运行；
4. 第四期：在前三期证明价值后再做可视化、审计、协作和规模化。

**对实现的约束：**

- 第一期闭环未完成，不进入第二期自动化；
- 没有持续产生价值，不建设完整产品界面；
- 没有长期安全记录，不开放自动正式启用；
- 没有真实的版本冲突，不建设多版本选择系统。

## 待确认问题

以下内容尚未形成最终决定，不能当作既定需求：

- 第一期实际使用哪一种 DeepSeek Harness 配置、模型和模型参数；
- 人工练习题具体选择哪些失败机制；
- 真实任务累计到多少数量或运行多久后开始第一次问题分析；
- 第一期允许候选使用哪些 Cordis 能力、哪些能力需要额外批准的具体清单；
- 事故测试和独立相似测试的具体文件格式；
- 第一批基础正常测试包含哪些代码任务；
- 人工修正问题卡片、测试和候选时，允许修改到什么程度；
- 第一阶段正式成功需要一个还是多个来自真实任务的有效改进；
- 模型调用、测试时间、磁盘占用和人工审查的预算上限；
- 真实任务日志和代码快照的隐私、保留与删除规则。

## 2026-08-17：第一期成功门槛

### D-013：第一期只要求一个高质量的真实改进

**状态：已确认**

第一期正式成功只要求产生一个来自未干预真实任务的有效改进，不要求用多个改进证明可重复性。能否持续产生多个有效改进由第二期验证。

这个真实改进必须完整满足：

- 系统主动从长期记录中发现问题；
- 问题具有实际意义，并得到人工认可；
- 冻结事故测试在旧版本失败；
- 候选版本通过事故测试；
- 候选版本通过至少一个未提前看见的独立相似测试；
- 一组原本正常的任务没有明显退化；
- 人工批准正式启用；
- 重启后改进仍然保留；
- 可以恢复上一个正式版本。

**对实现的约束：**

- 第一期不为凑候选数量扩大范围；
- 人工练习题产生的修改不能计入这一个真实改进；
- 只修复单个事故、不能推广到相似情况的候选不算完成；
- 进入第二期后再用多个问题和未来任务验证持续性。

### D-014：正式插件不能绕过现有安全和批准流程

**状态：已确认**

第一期候选插件在隔离的测试副本中，可以执行测试并修改临时文件。正式启用后，可以读取必要状态、监听事件、注册工具和改变智能体流程，但不能借助后台运行身份绕过 DeepSeek Harness 已有的安全检查和用户批准。

正式运行时：

- 必要的只读状态检查和受限只读命令可以开放；
- 修改文件、访问网络、调用外部系统等有副作用的行为，必须经过 Harness 原有工具和批准流程；
- 后台事件监听器不能静默执行不可恢复操作；
- 插件不得自行扩大权限或读取未授权的密钥。

**对实现的约束：**

- 测试环境和正式环境使用不同权限；
- 候选测试默认在可丢弃的工作区副本中进行；
- 正式插件需要声明其读取、命令、文件、网络和外部操作需求；
- 未声明或无法通过现有批准流程表达的副作用，第一期不允许执行。

### D-015：重复问题可以来自同一项目，但通用性必须换环境验证

**状态：已确认**

第一期不强制等待同一个问题在多个真实代码项目中出现。问题发现至少需要来自三个相互独立的真实任务，这些任务可以属于同一个项目。

候选是否具有 Harness 层通用性，需要通过内容不同的独立相似测试判断；条件允许时，独立测试使用另一个小型代码仓库或不同的代码环境。

**对实现的约束：**

- 同一次任务中的重复调用不能冒充多个独立支持案例；
- 同一项目中的三个独立任务足以触发问题分析；
- 独立相似测试不能复用事故任务中的项目名称、固定路径、私有符号或答案；
- 如果候选只在原项目有效，应标记为项目专用改进，不能宣称修复了通用 Harness 弱点；
- 项目专用改进可以保留研究记录，但不计入第一期要求的通用真实改进。

### D-016：每个真实实验任务提供轻量结果标记

**状态：已确认**

第一期实验期间，每个真实代码任务结束后尽量由使用者提供一个轻量结果标记：

```text
成功 / 部分成功 / 失败
可选的一句话说明
```

这个标记只提供最终结果，不代替系统自己分析任务过程和发现重复问题。

**对实现的约束：**

- 标记操作应足够简单，不能要求使用者填写复杂表单；
- 系统要区分运行错误、最终任务结果和用户评价，不能强行合并成一个分数；
- 没有人工结果标记的任务仍可用于分析明确的运行错误；
- 没有标记时，系统不能仅凭智能体声称完成就把任务作为强成功证据；
- 人工说明需要和对应任务、当时版本及相关步骤建立引用关系。

### D-017：本地保存、最小外送、代码快照按项目选择

**状态：已确认**

第一期采用以下数据原则：

- DeepSeek Harness 原有任务记录继续保存在本地；
- 自进化系统只额外保存问题摘要、证据位置、测试、候选和版本信息，不复制全部对话；
- 分析时只把当前问题需要的记录片段发送给已经在使用的同一个模型服务；
- 密钥、环境变量值和明显敏感字段不得进入分析材料；
- Git 或文件快照按项目明确选择，默认不保存完整工作目录；
- 使用者可以删除某个任务产生的派生经验和测试材料。

**对实现的约束：**

- 派生经验必须能够追溯到本地原始任务记录；
- 读取完整任务记录应当按需发生，不能默认把全部历史交给模型；
- 第一版只做必要的字段过滤和删除能力，不建设通用数据治理平台；
- 项目未授权代码快照时，验证只能使用现有任务记录、最小事故材料或未来相似任务；
- 删除派生材料不应改写 DeepSeek Harness 自己的原始任务日志。

### D-018：问题分析同时支持人工触发和空闲期自动运行

**状态：已确认，具体间隔待定**

第一期的问题分析提供两种入口：

1. 使用者可以随时主动触发；
2. 系统在累计了新的任务经验并且运行环境长时间空闲时，可以定期自动分析。

自动采集任务记录和更新简单统计不需要等待人工触发。自动深入分析的具体间隔、空闲判断时间和模型调用预算以后根据真实使用频率确定，不在当前阶段写死。

**对实现的约束：**

- 自动分析不能与正在进行的真实任务争夺关键资源；
- 没有新经验时不重复分析相同材料；
- 同一批经验不能产生多个并发分析任务；
- 自动分析必须有模型调用次数或费用上限；
- 人工触发与自动触发使用同一套分析流程和记录格式；
- 第一版保留关闭自动分析的简单开关。

### D-019：空闲期自动流程停在问题卡片

**状态：已确认**

第一期的空闲期自动分析只执行：

```text
读取新增经验
→ 发现重复现象
→ 生成问题卡片
→ 判断是否可能属于 Harness
→ 提示使用者存在待处理问题
```

生成事故测试、生成动态插件和启动验证，需要人在确认问题卡片后再继续。

**对实现的约束：**

- 自动分析不运行候选代码；
- 自动分析不修改正式配置；
- 问题卡片未确认前不进入测试和修改阶段；
- 使用者可以拒绝、搁置或标记证据不足；
- 自动分析失败只影响本次分析任务，不能影响正常代码任务。

### D-020：人工可以纠正事实，但不能代替系统完成关键发现

**状态：已确认**

人可以对系统生成的问题卡片和事故测试进行以下干预：

- 删除错误证据；
- 指出某项事实判断不成立；
- 补充真实任务结果；
- 删除敏感内容；
- 修正测试中的技术错误；
- 拒绝问题或要求系统重新生成。

如果人直接提供了根本原因、应该修改的 Cordis 能力、具体解决方案或候选插件的关键逻辑，这次结果仍可用于工程验证，但不能计入第一期要求的自主发现成果。

**对实现的约束：**

- 问题卡片和测试的人工修改保留修改前后内容；
- 记录修改人、时间和原因；
- 第一阶段研究报告要公开人工参与程度；
- 是否计入自主成果由人工参与记录判断，不能只看最终结果；
- 人工纠正事故测试后，仍需重新确认旧版本确实失败。

### D-021：第一期开工前建立小型基础考试

**状态：已确认**

第一期开工前准备 5～10 个固定的正常代码任务，作为所有候选都必须参加的基础考试。建议覆盖：

- 阅读和定位代码但不修改文件；
- 修复一个小错误并运行测试；
- 小范围重构并保持原有测试通过；
- 尊重工作区中已有的用户修改；
- 无法完成时正确说明，而不是假装成功。

这些任务需要先确认固定基线版本能够正常完成。

**对实现的约束：**

- 基础考试在候选生成前建立；
- 候选不能修改基础考试和评判规则；
- 基础考试使用可恢复的代码仓库或工作区副本；
- 第一版保持 5～10 个任务，不为追求覆盖率扩张成大型评测平台；
- 只有真实候选暴露出新的共性退化时，才向基础考试增加对应任务。

### D-022：关键测试重复，普通回归复用基线

**状态：已确认**

第一期采用控制成本的重复策略：

- 固定基线的基础考试提前运行并保存结果，不为每个候选重新运行旧版；
- 事故测试和独立相似测试，新旧版本至少各运行两次；
- 候选版本对 5～10 个基础正常任务先各运行一次；
- 某个任务结果不稳定时，再增加一次复测；
- 两次结果互相矛盾时，标记为证据不足，不能挑选最好的一次作为通过。

**对实现的约束：**

- 缓存的基线结果必须绑定 Harness、模型、配置和任务环境版本；
- 基线发生变化后，相关缓存失效并重新运行；
- 每次重复运行都保留独立结果，不能只保存汇总结论；
- 第一版不建设复杂统计平台；
- 后续只有在实际随机波动造成明显误判时，才增加重复次数或统计方法。

### D-023：同一个问题最多尝试三个串行候选版本

**状态：已确认**

第一期中，同一个问题最多自动生成三个候选版本。每次新版本只能根据上一个版本的明确测试失败或运行诊断进行修正。

三个候选版本都失败后，停止自动尝试并把问题标记为“当前无法解决”。是否以后重新开启由人决定。

**对实现的约束：**

- 候选版本串行生成和验证；
- 不同时生成多个候选互相竞争；
- 每次修正保留父版本、失败证据和修改内容；
- 失败次数按一个问题计算，不能通过创建新问题标识绕过上限；
- 人工重新开启时必须记录原因；
- 第一版不实现候选合并、群体搜索或无限自我修复循环。

### D-024：第一期不做独立控制台，但必须有明显状态提示

**状态：已确认**

第一期不建设专门的自进化管理页面、趋势仪表盘或完整审批中心，但必须在 DeepSeek Harness 现有界面中提供明显、持续可见的状态提示，让用户知道自进化管理是否开启、当前是否正在分析或测试，以及是否在等待人工处理。

状态提示可以使用醒目的文字、颜色、标记或现有界面位置中的小型状态条实现。

**对实现的约束：**

- 自进化管理开启时不能完全隐形运行；
- 状态提示不得只依赖颜色，还要有明确文字，避免颜色识别和无障碍问题；
- 不为状态提示建设新的页面和导航系统；
- 正常经验采集、分析或测试状态发生变化时，提示应及时更新；
- 候选需要人工确认或发生异常时，必须有明显提醒；
- 具体放置位置和视觉形式在查看当时可用的 Cordis 界面插槽后选择最小实现。

### D-025：自进化开启后状态标记始终可见

**状态：已确认**

自进化功能开启后，状态标记始终显示。正常空闲采集期间也不能消失，避免用户无法区分“正在正常记录经验”和“功能没有运行”。

第一期至少区分：

- 自进化记录中；
- 正在分析；
- 正在测试候选；
- 等待用户确认；
- 自进化已暂停或发生错误。

**对实现的约束：**

- 平时状态可以低干扰显示；
- 分析、测试、等待确认和错误状态应更加醒目；
- 状态必须同时使用文字和视觉变化，不能只依赖颜色；
- 状态来源必须是实际运行状态，不能使用与后台任务脱节的界面假状态。

### D-026：候选必须在独立进程和可丢弃工作区中试运行

**状态：已确认**

候选插件不能直接装入正在处理真实任务的主进程中试错。第一期采用：

- 主进程负责真实任务、经验采集和问题分析；
- 独立 DeepSeek Harness 测试进程负责加载旧版本和候选版本；
- 代码任务使用临时工作区、Git 工作树或其他可丢弃副本；
- 测试结束后可以销毁测试进程和临时工作区；
- 候选通过验证并得到人工批准后，才进入正式运行环境。

**对实现的约束：**

- 测试进程不使用生产密钥和不必要的网络权限；
- 旧版本和候选版本使用相同的任务材料、模型、配置和环境基线；
- 测试失败不能改变主进程的正式插件和配置；
- 测试进程异常退出后必须能够清理临时资源；
- 第一版复用现有进程启动、配置和工作区能力，不建设通用云端沙箱平台。

## 2026-08-18：版本生效范围

### D-027：批准后的新版本只对新会话生效

**状态：已确认**

候选获得批准后，只对批准后新创建的任务会话生效。已经进行中的会话继续使用它启动时的 Harness 版本，不在任务中途切换插件能力。

如果使用者希望立即使用新版本，应新建任务会话。

**对实现的约束：**

- 每个会话记录启动时使用的正式版本；
- 正式版本切换不能重新挂载到旧会话；
- 新旧会话可以在同一进程中并存时，插件作用范围必须能够按会话区分；
- 如果现有 Cordis 插件机制无法安全支持同一进程中的版本并存，第一版通过新进程或新运行实例应用新版本，不能静默污染旧会话；
- 经验和测试结果必须记录实际作用于任务的版本，不能只读取当前全局版本。

### D-028：离线通过后直接用于新会话并进入观察期

**状态：已确认**

候选通过冻结事故测试、独立相似测试和基础考试并获得人工批准后，直接成为所有新会话的默认版本，同时标记为“观察中”。

不要求真实用户重新执行任务、选择试用版本、寻找相似任务或配合额外研究流程。后续效果从用户自然发生的真实任务中被动观察。

观察期间：

- 明确的插件加载失败、运行环境崩溃和基础检查失败可以自动恢复旧版本；
- 系统继续采集正常任务记录和轻量结果标记；
- 再次出现原问题或出现明显新问题时提醒人工处理；
- 没有自然出现合适的相似任务时，只标记“后续证据尚未增加”，不要求用户制造任务；
- 普通行为效果变化不因少量样本自动切换版本。

**对实现的约束：**

- 第一阶段不建设人工选择任务的试用流量系统；
- 第一阶段不要求用户理解候选版本或研究实验流程；
- 状态提示需要区分“正式稳定”和“正式观察中”；
- 观察期是正式启用后的证据积累状态，不是阻塞上线的额外审批阶段；
- 第一阶段成功门槛仍以离线验证、人工批准、跨重启保留和可恢复为准，未来自然任务用于增加或推翻长期证据。

### D-029：改进记录永久独立，运行插件按真实需要整理

**状态：已确认**

第一期采用一个改进对应一个独立 Cordis 插件，便于判断效果、单独停用和恢复。长期不要求运行环境永久保持一个问题一个插件。

每条改进的问题、证据、事故测试、独立相似测试和版本历史始终独立保留。只有在真实出现管理或性能问题后，才可以把已经稳定、作用位置相同、能力归属相同的运行逻辑整理进较少的正式插件。

**对实现的约束：**

- 第一期不建设自动合并能力；
- 历史上存在的插件不等于运行时全部加载，已取代、已停用和已合并版本只保留记录；
- 不能只因为插件数量看起来多就合并；
- 合并需要由启动开销、运行开销、重复监听或管理困难等真实证据触发；
- 合并后的插件视为一个新候选，必须重新运行相关事故测试、独立相似测试和基础考试；
- 合并不能丢失每条原始改进与代码、测试之间的对应关系。

### D-030：技术故障自动恢复，行为退化由人决定

**状态：已确认**

观察期内，插件加载失败、导致进程崩溃或破坏基础运行检查等明确技术故障，系统可以立即自动恢复上一个正式版本。

用户认为结果不好、任务失败、步骤增多或再次出现原问题等行为信号，第一期只记录并明显提醒，不自动停用插件。由人查看证据后决定继续观察、暂停插件、恢复旧版本或针对新问题生成事故测试。

**对实现的约束：**

- 自动恢复只使用能够客观判断的技术条件；
- 行为失败不能在缺少因果证据时直接归咎于最新插件；
- 自动恢复和人工恢复都保留原因、时间、版本和相关运行记录；
- 发生技术故障后不能删除坏版本和失败证据；
- 第一版不建设基于少量行为分数自动来回切换版本的机制。

### D-031：第一期只准备一个人工练习题

**状态：已确认**

第一期只准备一个人工练习题：“智能体修改代码后没有进行要求的验证就宣布完成”。这个练习题使用固定任务材料或模型回放，保证旧版本能够重复表现出预先知道的问题。

它只用于检查以下工程流程能否完整运行：

```text
采集人工任务记录
→ 发现重复问题
→ 生成问题卡片
→ 生成并冻结事故测试
→ 确认旧版本失败
→ 创建 Cordis 候选插件
→ 确认新版本通过
→ 保存正式插件
→ 模拟故障并恢复
```

**对实现的约束：**

- 所有人工练习任务明确标记为人工构造；
- 人工练习数据不能进入真实经验统计；
- 人工练习产生的插件不能计入第一期要求的真实改进；
- 第一期开工时不预先建设另外两个练习题；
- 只有这一个练习题无法覆盖某个必需工程环节时，才增加第二个练习题。

### D-032：任务执行和自进化步骤使用同一个固定模型

**状态：已确认**

第一期中，执行真实代码任务、分析长期经验、生成事故测试和生成 Cordis 候选插件都使用同一个固定模型。

分析、测试和候选生成使用相互隔离的上下文，但不通过后台换用更强模型提高结果。

**对实现的约束：**

- 每次任务和自进化步骤记录实际模型及其主要参数；
- 模型版本变化后，未完成候选需要重新建立验证基线；
- 三个隔离步骤不能共享不应提前看见的测试和答案；
- 第一阶段研究结论要说明任务模型和自进化模型相同；
- 如果固定模型无法可靠生成插件，先记录为研究结果，不能静默换模型；是否增加更强的 Harness 工程模型作为对照实验留到后续决定。

### D-033：第一期结束前保留全部派生研究材料

**状态：已确认**

第一期结束前，默认保留问题卡片、证据引用、事故测试、独立相似测试、候选插件、失败版本、评估结果、批准和恢复记录，不自动清理。

失败候选同样保留，用于复盘系统尝试过什么、为什么失败以及是否重复提出相同方案。

**对实现的约束：**

- 完整代码快照仍然按项目授权，不能因本决定默认长期保存；
- 设置简单磁盘空间上限，接近上限时提醒人工处理，不静默删除研究材料；
- 使用者可以手动删除指定任务的派生材料；
- 删除行为需要留下最小审计记录，但不保留被要求删除的敏感正文；
- 第一期结束后再根据实际数据量、研究需要和隐私风险决定长期保留期限，不提前建设复杂清理策略。

### D-034：项目作为独立扩展，不维护 DeepSeek Harness 分叉

**状态：已确认**

自进化项目作为独立扩展项目依赖固定的 DeepSeek Harness 官方版本，不直接开发和长期维护 DeepSeek Harness 核心源码分叉。

项目由以下部分组成：

```text
DeepSeek Harness 官方版本
        +
自进化控制插件
        +
系统生成并批准的正式 Cordis 插件
```

**对实现的约束：**

- 官方仓库可以作为本地源码参考和测试依赖；
- 自进化实现和生成插件拥有独立的代码、版本和发布记录；
- 第一阶段不把新包直接塞入官方单体仓库；
- 固定记录依赖的官方提交版本；
- 官方版本升级时重新运行兼容性和基础考试；
- 只有真实重复问题被证明无法通过公开 Cordis 能力解决时，才重新评估源码级候选或维护分叉。

### D-035：累计 30 个真实代码任务后进行正式复盘

累计 30 个带有结果标记的真实代码任务后，必须进行一次正式复盘。

复盘至少判断：

- 是否出现由三个独立任务支持的重复问题；
- 问题是否属于 Harness；
- 是否能够制作可靠事故测试；
- 是否值得继续收集同类任务；
- 是否需要调整问题发现方法。

**对实现的约束：**

- 只统计未被标记为人工练习的真实任务；
- 缺少结果标记的任务不计入这 30 个正式样本；
- 30 个任务后没有合格问题时，不自动宣布项目失败；
- 不能为了完成里程碑降低重复次数、测试或通用性标准；
- 复盘结果可以是继续收集、调整方法或暂停项目，并记录理由。

第一期执行真实代码任务、分析经验、生成事故测试和生成 Cordis 候选插件，统一使用官方 `deepseek-official` 路线下的 `deepseek-v4-flash` 模型。

不采用此前建议的 DeepSeek-V4-Pro。

- 后续如需使用 Pro，只能作为新的对照实验或下一阶段决定，不能与第一期结果混合统计。

### D-037：真实任务使用 PTC 模式，候选生成使用创造模式

第一期按照工作阶段使用不同的 DeepSeek Harness 预设，但所有阶段统一使用 DeepSeek-V4-Flash：

- 真实代码任务使用 PTC 模式，产生主要真实经验；
- 长期经验分析和事故测试生成使用隔离的分析上下文；
- Cordis 候选插件生成、修改和诊断使用创造模式；

极简模式不作为第一期主要实验对象，可以在以后作为简单 Harness 对照组。

**对实现的约束：**

- 真实任务期间不暴露创造模式的动态插件修改工具，避免任务执行和自我修改混在一起；

- 不同阶段虽然工具不同，但模型身份和基线参数保持固定；
- 每条任务记录标明实际使用的预设；
- PTC 模式产生的组合工具执行记录必须能够被经验采集和事故测试读取；
- 模式差异不能被当作候选插件带来的效果。

## 2026-08-20：第一期运行入口与开工前修正

### D-038：第一期只支持官方网页界面，并使用项目启动命令

**状态：已确认**

第一期只支持 DeepSeek Harness 官方网页界面。使用者通过本项目提供的启动命令进入带自进化能力的运行环境，不要求同时兼容无界面的单次运行方式或其他入口。

**对实现的约束：**

- 常驻状态、任务结果标记、问题确认和候选审查都以官方网页界面为唯一交互面；
- 项目启动命令负责准备固定配置、正式插件清单并启动官方网页界面；
- 启动命令外层承担启动健康检查。新正式插件导致 Harness 无法启动时，外层恢复上一个启用清单后重启；
- 第一版不建设通用守护进程、集群管理或多入口适配层；
- 后续只有确有无界面运行需求时，才增加第二种入口。

### D-039：动态候选必须物化成标准插件并重新验证

**状态：已确认**

本决定细化并取代 D-009 中“批准后直接转为磁盘插件”的执行顺序；D-009 关于“动态创造只用于试验、正式能力必须持久化”的原则仍然有效。

创造模式生成的动态 Cordis 包只是试验产物，不能靠复制源码直接成为正式插件。动态候选初步通过后，系统应把它生成为 DeepSeek Harness 可正常安装和加载的标准本地插件包，再用这个标准插件形态重新运行完整验证。只有重新验证通过后才允许人工批准并加入启用清单。

**对实现的约束：**

- 标准插件至少包含插件入口、包清单和 Cordis 配置层；
- 标准插件复测覆盖生命周期、事故测试、独立相似测试和基础考试；
- 动态候选通过、标准插件复测通过是两个不同状态，不能合并记录；
- 正式发布不允许模型直接修改当前启用清单；
- 第一期只支持能够物化为普通插件的候选，无法物化的候选标记为当前不支持。

### D-040：第一期隔离防误伤，不宣称抵御恶意代码

**状态：已确认**

第一期通过独立进程、临时工作区、最少环境变量、无生产密钥和受限能力降低候选误伤真实任务的风险。进程隔离和 DeepSeek Harness 的动态执行环境都不是完整安全边界，因此第一期不宣称可以安全执行恶意候选代码。

**对实现的约束：**

- 候选只作为受监督的实验代码运行；
- 测试进程不继承生产密钥，环境变量使用明确允许清单；
- 不需要的文件、命令和网络能力不提供给候选；
- 如果现有运行方式无法可靠禁止某项系统能力，界面和记录必须如实说明，而不是显示为已隔离；
- 容器、操作系统级网络限制和恶意代码防护留到真实需要出现后再做。

### D-041：正式开发前先完成五项接口小验证

**状态：已确认**

正式铺开第一期功能前，先用最小代码验证五个最脆弱的连接点：控制插件装载、真实会话记录读取、网页常驻状态、独立创造模式候选运行、标准插件跨重启与启动失败恢复。

小验证只回答架构是否走得通，不建设经验分析、问题卡片、通用账本或完整验证平台。五项全部通过后再进入里程碑一；任何一项失败都先修正设计，不用外围功能掩盖。

对应实施计划：[里程碑零实施计划](./2026-08-20-milestone-zero-implementation-plan.md)。

## 2026-09-19：逐项对齐后的修订

以下决定来自本轮逐项确认。D-001 至 D-041 保留为历史；发生冲突时，按以下明确标注的取代范围执行。产品、技术、路线图和里程碑零实施计划同步更新，文档更新不代表相关能力已经实现。

### D-042：如实报告失败也算改进，但不能以退化正常能力为代价

**状态：已确认；细化 D-013、D-021、D-022**

减少假完成、识别并如实报告失败，本身就是有价值的改进，不要求每次都把原本做不成的任务做成。允许稍微变慢，但不能明显增加对用户的打断，也不能让原本能完成的任务变得做不成。

**原因：** 防止误导用户有实际价值，但不能通过一律拒绝、反复询问或永不结束来通过考试。

**对实现的约束：**

- 任务完成结果与插件改进效果分别记录；任务仍然失败，不得改记为任务成功；
- 测试检查行为是否正确、任务是否合理结束，不能只检查是否执行了某条命令；
- 正常任务回归同时检查完成情况、额外打断和耗时；具体容忍范围在该轮测试冻结时记录，不在看到结果后放宽；
- 正式启用仍需通过未见过的相似任务，原题通过不能代替通用性验证。

### D-043：失败题可以用于学习，但暴露后必须换新题验收

**状态：已确认；细化并取代 D-006、D-007、D-011 中固定一份隐藏测试反复用于后续候选验收的解释**

独立相似测试失败后，可以把具体错误告诉候选生成步骤帮助修复；已暴露的题目转为公开回归，不能再作为最终独立验收证据。下一版候选必须使用未见过的新相似测试。

**原因：** 既允许从失败中学习，又避免把记住考题误判为能力改善。

**对实现的约束：**

- 每版测试包仍先于对应候选生成或修改冻结；新相似测试由隔离测试上下文生成，候选不可见；
- 保留旧题、失败结果、暴露时间和新题来源，不修改或删除失败来配合候选；
- 已公开题目继续用于回归；新题失败时不能仅凭原题通过正式启用；
- 最终标准插件也必须有未用于其生成或修复的独立测试证据；物化或修复步骤接触题目细节后同样需要换题；
- 换题或物化不能重置同一问题的候选次数限制；不是为了选出好结果而不断换题重考。

### D-044：最多三版，并且每次尝试有时间和消耗上限

**状态：已确认；重申 D-023，扩展 D-018 的预算约束**

同一问题最多尝试三个串行候选版本。三版均未通过就停止、保留记录，由操作者决定是否以后继续。每次尝试同时设置时间和消耗上限，先达到哪个就停止，不能只提醒后继续运行。

**原因：** 限制候选数量不能防止某一版无限等待或持续消耗。

**对实现的约束：**

- 时间、模型调用或 token 等消耗限额在首次试跑前确定并记录，不在本轮文档中臆定数值；
- 一次尝试的预算覆盖测试准备、生成、修复、物化和验证等相关工作，子步骤不能另开预算绕过上限；
- 达到上限后停止相关执行、保留已产生证据并等待人工决定，不自动开启下一版；
- 超时、预算耗尽和测试行为失败分开记录；继续或重新开启必须留痕。

### D-045：明确技术故障时，先暂停受影响任务再恢复旧插件

**状态：已确认；细化 D-030、D-038，取代 D-027 中旧会话在明确故障时仍继续使用坏插件的解释**

新插件出现明确技术故障时，暂停受影响的任务，恢复旧插件，再提示操作者继续处理。正常发布仍只影响新会话；故障处置不能让已挂载坏插件的任务继续运行。

**原因：** 切换新任务的默认版本不能消除正在运行的故障插件。

**对实现的约束：**

- 不把“启用清单已切回”当成恢复完成，必须确认坏插件停止作用；无法安全卸载时停止受影响实例并以旧集合重启；
- 外部启动器承担控制插件无法运行时的恢复，包括已确认由新插件引发的进程退出；不依赖已崩溃的进程自救；
- 恢复后保留中断状态和证据，提示用户决定如何继续，不自动重放中断任务的副作用；
- 行为变差仍由人判断，不把普通任务失败、网络故障或额度不足直接归咎于新插件。

### D-046：自动撤销归属明确且没有后续改动的文件修改

**状态：已确认；补充 D-014、D-017、D-030**

恢复插件版本与撤销文件修改是两件事。自动撤销能明确归属于故障插件、且之后未被用户或其他任务修改的文件变更。归属不清，或已有后续改动的文件，保留现场并交给用户处理，不尝试自动合并式撤销。

**原因：** 尽量减少故障损失，同时保护用户已有和后续的正常工作。

**对实现的约束：**

- 自动撤销依赖可核对的操作来源、修改前内容和修改后状态；仅凭修改时间或当前 Git diff 不足以证明归属；
- 只保存按项目授权所需的最小恢复材料，不因此默认保存完整工作区；缺少材料时转人工处理；
- 撤销前确认没有后续修改并防止撤销期间并发写入；无法确认时跳过该文件；
- 不自动恢复整个仓库，不覆盖用户后续修改；报告已撤销、跳过和失败的项目；
- 恢复失败或部分成功必须如实显示，不宣称所有影响已消除。

### D-047：不可撤销的外部操作逐次批准

**状态：已确认；细化 D-014**

第一版生成的插件不得自动执行发消息、提交外部数据等不可撤销的外部操作；需要执行时，每次单独取得用户批准。

**原因：** 插件获准启用，不等于其未来每次外部操作都获准；恢复旧插件也撤不回已发生的外部影响。

**对实现的约束：**

- 通过现有工具和批准流程表达每次具体操作；无法表达逐次批准的操作不执行；
- 隔离验证使用替身或可丢弃目标，不向真实外部系统试写；
- 不把插件启用批准、后台监听身份或恢复流程作为跳过批准的理由。

### D-048：区分自主发现与人指出的问题，同一任务重试只计一次

**状态：已确认；细化 D-002、D-004、D-015、D-020、D-035**

人先指出的问题也可以修复并按同样标准验证后使用，但要标记为“人指出问题后的改进”，不能计入自主发现成果。同一件工作重试多次，即使跨轮次或会话，同一问题也只算一个支持案例。

**原因：** 改进是否有用与问题由谁发现分别记录，避免把重试次数或系统自己的练习当成真实发现证据。

**对实现的约束：**

- 区分真实任务、人工练习、内部分析、测试生成、候选生成和评估；内部研究记录不进入真实样本统计；
- 支持案例按实际任务归并，不能直接用 `turn/end` 数量或会话数量计数；
- 同一任务的重试不增加三个支持案例和三十个真实任务复盘的计数；
- 人工触发“开始分析”不等于人提供问题；人工先指出问题、根因或关键方案时须记录来源并排除自主成果资格。

### D-049：先验证真实发现能力，再补自动调度和完整交互

**状态：已确认；细化 D-041，取代 D-018、D-024 及既有里程碑中必须先完成自动调度和完整操作流程才能验证真实发现能力的顺序**

先补完必要的运行与恢复验证，再用真实记录试验问题发现能力。初期由操作者点击或通过现有界面命令触发分析；系统自己提出问题。空闲期自动分析和完整操作交互后补。

**原因：** 尽早确认系统能发现值得修的问题，避免外围流程建好后才发现核心研究假设不成立。

**对实现的约束：**

- 里程碑零仍先完成必要连接点，纳入本轮确认的停止、恢复和文件撤销边界演练；
- 最小采集、来源标记、任务归并、结果标记和真实状态提示到位后，立即进行人工触发的真实发现试验；
- 不等待完整账本、候选审查界面或自动定时分析才开始该试验；
- 三个独立真实任务和三十个任务复盘口径不变；三十个任务是正式复盘点，不是首次分析门槛；
- 自动触发后补不降低自主发现的标准，也不降低正式发布所需的测试、批准与恢复要求；
- 未经本轮确认的其他审查建议不自动升级为已确认需求。D-039 的标准插件完整复测要求保持不变。
