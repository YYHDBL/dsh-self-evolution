# Continually Self-Evolving DeepSeek Harness 分期路线图

> 状态：已按 2026-09-19 决策 D-042 至 D-061 修订，版本 1.7  
> 新版目标：`ddefc45` / `0.1.6-alpha.2`；实际运行仍为 `47f9438`，新版需通过[兼容性验收](../research/2026-09-19-harness-upstream-compatibility.md)  
> 项目性质：研究原型优先，成功后再发展为内部系统和产品  
> 权威依据：[项目决策记录](./2026-08-17-project-decision-log.md)

本轮取舍（D-051～D-054）：控制插件保持轻量，分析和测试编排放入按需工作进程；有适用材料时前置廉价回放；升级前关闭并核验附带日志上传；敏感记录不进入 Git。不新增完整命令行工作台，真实发现试验仍优先。

本轮补充 D-058～D-060：实施前落实[证据捕获、试用与成本合同](./2026-09-19-evolution-evidence-contract.md)。默认试用最多纳入 5 个实际任务或启用后 7 天，先到为准；到期复盘不等于成功。各阶段实际 token/时长及未知消耗独立记账；必要捕获探针须在首次真实候选对照前通过。

## 1. 最终蓝图

为成熟 DeepSeek Harness 增加受控制的自进化能力：从真实任务发现业务适配机会，选择 Memory、Skill、配置或插件等最小改动，以真实关键步骤对照和有限试用积累证据，人工决定保留或恢复。先聚焦代码任务，不把报错和 SOP 当作全部机会。

```text
真实任务
→ 长期经验
→ 适配机会
→ 冻结验证计划
→ 最小改动
→ 适用检查与关键步骤对照
→ 人工批准有限试用
→ 真实使用复盘
→ 保留或恢复
```

每个正式改进必须能够回答：

1. 为什么要改？
2. 证据来自哪些真实任务？
3. 修改前为什么不行？
4. 修改后如何证明更好？
5. 如果改坏了，怎样恢复？

## 2. 四期路线

| 阶段 | 核心问题 | 结束时必须证明 |
|---|---|---|
| 第一期：真实闭环 | 这条路线是否可行？ | 一个真实问题变成可验证、可持久、可恢复的改进 |
| 第二期：持续价值 | 成功是否可以重复？ | 多个不同问题持续产生有效改进 |
| 第三期：可靠半自动 | 能否减少人工而不失控？ | 低风险流程自动运行，正式权限按风险开放 |
| 第四期：产品化 | 别的团队能否理解和使用？ | 可视化、审计、协作、部署和成本收益成立 |

阶段纪律：

1. 第一期没有真实闭环，不进入第二期扩张；
2. 没有持续产生价值，不建设完整产品界面；
3. 没有长期安全记录，不开放自动正式批准；
4. 没有真实插件冲突，不建设多版本选择和自动合并；
5. 新复杂度只能解决已经出现的实际瓶颈。

## 3. 第一期：证明一个真实闭环

### 3.1 研究目标

使用同一个 DeepSeek-V4-Flash：

- 在 PTC 模式执行真实代码任务；
- 从长期记录中主动发现问题；
- 在隔离上下文整理真实证据和验证计划；
- 选择最小改动；需要插件时用 Creator；
- 在独立进程比较新旧版本；
- 冻结产物，完成适用离线复验，批准有限试用后收集实际效果证据。

第一期只要求一个高质量真实改进。人工练习题只能证明工程管道可用，不计入研究成果。

减少假完成、如实报告失败也算有价值的改进；允许稍微变慢，但不能明显增加打断或损害正常完成能力。先完成必要运行与恢复验证，再用真实记录人工触发系统发现问题；自动调度和完整操作交互后补。

本轮 D-061：从失败、低效成功和高质量成功三类记录找机会；Jev 批量评价、Skill 委派、上下文删减仅为可选实验，不并列列入 MVP 必交付。先围绕一个真实机会完成一条路径，分别验收流程和效果。实施交接见[实施规划交接说明](./2026-09-19-implementation-handoff.md)。

### 3.2 必须交付

- 常驻且明显的自进化状态标记；
- 任务结果的成功、部分成功、失败轻量标记；
- 原始会话日志的增量经验采集；
- 真实任务、人工练习与内部研究严格隔离，同一工作重试归并；
- 人工触发的问题分析先交付，真实发现能力验证后补空闲期自动触发；
- 至少三个独立任务支持的问题卡片；
- 人工确认与修改留痕；
- 每版修改前冻结验证计划和可用独立材料；暴露材料不再充当独立证据；
- Memory、Skill、配置或插件的最小候选改动；
- 独立进程和可丢弃工作区验证；
- 按影响面选择真实正常材料、反例及适用工程回归；
- 产物冻结及适用离线复验，证据分层记录；
- 新版本只用于新会话；
- 试用范围、期限、预算、退出条件与人工复盘；
- 明确技术故障暂停受影响任务并恢复；只自动撤销归属明确且无后续改动的文件；
- 同一问题最多三版，每次尝试同时受时间和消耗上限约束；
- 证据、失败候选和版本历史。

### 3.3 开工前小验证与五个里程碑

#### 里程碑零：开工前接口小验证

验证控制插件装载、真实会话记录读取、网页常驻状态、独立创造模式运行、标准插件跨重启和外部恢复。以最小演练覆盖尝试超限停止、明确运行故障暂停与文件撤销边界，不建设完整控制流程。全部通过后进入真实发现试验。

按新版重验客户端探针、handle 读取与 V3 日志迁移；创造模式直接生成标准 bundle，只安装到隔离测试 profile。旧版证据保留但不当作新版验收结果，兼容性通过前不切换实际运行基线。

#### 里程碑一：最小采集与真实发现试验

先具备不干扰正常工作的采集、真实状态、来源隔离、任务归并和轻量结果标记，随后立即用真实记录人工触发分析。由系统自己提出问题，保留证据和人工干预记录；不等待完整账本、审批交互或自动调度。没有合格发现时先复盘发现方法，不靠增加外围功能代替研究进展。

#### 里程碑二：人工练习闭环

使用一个固定练习题“修改代码后没有验证就宣布完成”，走通问题卡片、测试冻结和旧版失败确认。练习材料不进入真实统计。

#### 里程碑三：候选生成与隔离验证

生成一个最小改动；需要插件时用 Flash Creator。完成适用运行检查和真实关键步骤对照，结果与局限如实记录，不用小仓库代替业务证据。开发失败不能影响主进程。

#### 里程碑四：持久保存与恢复

候选冻结后在干净实例通过适用离线检查，经人工批准只对限定范围的新会话试用。不得以主 profile 的 Plugin Manager 热安装代替会话级发布。明确故障时暂停受影响任务并停止坏插件，控制插件无法运行时由外部启动器恢复；文件撤销保护用户后续修改。

#### 里程碑五：真实研究证明

系统从未干预真实代码任务中主动发现一个有意义问题，并完成全部闭环。累计 30 个有结果标记的真实任务后进行正式复盘。

三十个任务是正式复盘点，不是首次分析门槛。真实发现能力验证后补空闲期自动分析和完整操作交互；人工触发不等于人工提供问题。

### 3.4 第一期成功门槛

- 问题来自真实任务；
- 至少三个独立任务支持；
- 人未先指出问题，也未提供关键根因和解决方案；
- 验证计划在候选前冻结，正确依据可回查；
- 适用运行检查通过，局部对照及其局限如实记录；
- 有后续真实使用支持，负面结果、成本与人工纠正一并报告；
- 独立证据与已参与修复材料分开，没有证据不能判成功；
- 候选得到人工批准；
- 新版本跨重启保留；
- 故障暂停与插件恢复成功，文件撤销不覆盖后续正常修改。

人指出的问题也可通过相同验证后使用，但不计入自主发现成果。不可撤销外部操作须逐次批准，插件启用批准不能替代。

### 3.5 第一期明确不做

- 不修改 DeepSeek Harness 核心源码；
- 不维护官方仓库分叉；
- 不做完整环境保存平台；
- 不做通用任务评分器；
- 不做多智能体演化团队；
- 不做多候选并行竞争；
- 不做候选自动合并；
- 不建通用试用流量平台；按事前条件纳入自然任务，不事后挑结果；
- 不要求用户重复真实工作；
- 不做自动正式批准；
- 不做独立管理页面；
- 不做商业化多用户能力。

完整要求见：[第一期产品设计](./2026-08-18-phase-1-product-design.md)。

Jev 只列可选初筛试验，不阻塞 MVP；先验证漏判、成本和延迟。运行通过、局部有效、真实使用支持分开报告，不承诺小样本已证明普遍提升。

## 4. 第二期：证明持续产生价值

### 4.1 目标

证明第一期不是偶然成功，系统能够处理多种问题，并积累独立真实证据及有效的受管理改动，而非追求插件数量。

### 4.2 重点能力

- 扩大经验来源：任务截断、步骤浪费、恢复方式和可验证成功模式；
- 增加最小环境材料：工具返回、Git 提交和必要文件快照；
- 改进 Harness 问题与模型、环境问题的区分；
- 持续积累真实事故测试；
- 识别失败候选和重复坏方案；
- 从正式观察数据判断旧问题是否复发；
- 处理多个独立正式插件的相互影响；
- 根据真实成本决定分析频率和保留期限。

### 4.3 阶段门槛

- 至少处理三类不同重复问题；
- 至少产生三个完整候选；
- 至少两个改进在后续自然任务中继续获得支持；
- 系统能够主动放弃证据不足的问题；
- 回归库稳定积累真实事故；
- 多个正式插件共同运行没有破坏基础任务。

### 4.4 仍然不做

- 不默认自动正式批准；
- 不建设没有真实需求的多版本路由；
- 不把所有任务压成统一分数；
- 不开放安全、权限和核心流程的自动修改。

## 5. 第三期：可靠的半自动运行

### 5.1 目标

让低风险改进能够自动完成发现、测试、候选生成和正式观察前准备，同时保持高风险决策受控。

### 5.2 重点能力

- 低风险流程自动推进；
- 修改风险分级；
- 更可靠的空闲任务调度和费用控制；
- 插件、采集、测试队列和存储健康监控；
- 官方 Harness、模型和配置变化后的重新基线；
- 更完整的隐私、删除和保留策略；
- 真实出现开销后，对稳定同类插件进行整理；
- 对长期无误的低风险类别逐步开放自动正式批准。

### 5.3 风险分级方向

| 风险 | 示例 | 长期权限方向 |
|---|---|---|
| 低 | 提示、只读检查、辅助界面 | 有长期安全记录后可自动批准 |
| 中 | 改变执行流程、调用工具、写文件 | 保持人工批准 |
| 高 | 权限、安全、密钥、外部写入、核心流程 | 永不自动批准 |

### 5.4 阶段门槛

- 连续运行一个月不影响正常任务；
- 低风险候选能够自动完成离线验证并等待批准；
- 候选失败不会污染正式环境；
- 结构性故障能够可靠恢复；
- 每个正式改进均有完整证据和操作记录；
- 人工工作降为审查问题、结果和权限，而非亲自执行每一步。

## 6. 第四期：产品化和规模化

第四期只在前三期证明真实价值后启动。

### 6.1 重点能力

- 问题、证据、测试、候选和版本的可视化；
- 团队审批、权限与审计；
- 通知、维护和成本报告；
- 外部团队部署和升级；
- 真实出现任务分化后，再增加专门版本和保守选择机制；
- 衡量节省的返工、人工时间和模型费用。

### 6.2 阶段门槛

- 不了解内部代码的使用者也能理解改进原因；
- 能独立批准、暂停和恢复；
- 另一个团队可以部署和使用；
- 改进收益明显高于模型调用、测试和人工审查成本。

## 7. 功能优先级

| 优先级 | 能力 | 原因 |
|---|---|---|
| 最高 | 可靠经验记录 | 没有事实就没有自进化 |
| 最高 | 验证计划先行与独立真实证据 | 防止自评和针对材料写死 |
| 最高 | 隔离候选执行 | 防止实验破坏真实任务 |
| 最高 | 持久保存与恢复 | 改进必须能保留也能撤销 |
| 最高 | 采集和分析不影响主任务 | 长期运行的前提 |
| 最高 | 真实问题发现试验 | 必要运行与恢复验证后立即开展，先证明核心价值 |
| 较高 | 最小改动选择与受管理发布 | 文本、配置、插件按需求选择 |
| 较高 | 基础考试与失败历史 | 防止局部修复制造新问题 |
| 中等 | 风险分级和更多自动化 | 闭环可靠后再提高效率 |
| 较低 | 完整界面和团队协作 | 证明价值后再投入 |
| 很低 | 多版本路由和自动合并 | 只有真实冲突出现后才需要 |
