## 1. 一句话说明

第一期探索一个从真实使用中发现适配机会、修改模型之外的做事方法、以有限证据逐步验证并保留改进的自进化系统。改动包括 Memory、Skill、配置、上下文组织、工具和流程插件，不以生成插件数量衡量成功。

允许范围不等于第一期同时实现所有修改器：先围绕首个真实机会打通所需的一种改动路径，其他按需补充。

先聚焦真实代码任务，设计不把报错或编码检查作为唯一信号。既找失败，也找反复纠正、重复探索和成功任务中的不必要成本；成熟 Harness 是起点，不假定它缺基础功能。临时要求不能自动变成通用规则。

本版依据 D-055～D-057 修订范围、模型分工和验证方式；D-042～D-054 中未被明确取代的预算、隐私、批准、恢复与任务归并约束仍适用。目标上游与实际运行状态不因文档修订改变。

## 2. 第一期必须证明什么

研究问题：固定任务模型时，系统能否自己发现一个有价值的业务适配机会，选择最小改动，并在真实使用中获得支持它有用的证据？

一个合格闭环要求：

1. 机会来自真实任务，至少三个独立任务支持重复现象；同一工作重试只算一次。
2. 记录发现来源；人先指出的问题可以改善，但不计自主发现。
3. 模型提出带证据的假设和反例，不把 Harness/模型归因当作已证明因果。
4. 候选前固定目标、范围、验证办法、不可退化条件和停止标准。
5. 生成一个最小、可观察、可撤回的改动，并通过最终产物适用的运行与离线检查。
6. 经人批准，在限定的新任务范围和期限内试用；任务不足就记为待观察。
7. 有后续真实使用证据，报告改善、负面结果、样本限制和人工贡献，由人决定保留或恢复。
8. 改动可持久保存，明确技术故障能暂停和恢复，文件撤销不覆盖后续正常修改。

证据分“运行检查通过”“局部对照支持”“后续真实使用支持”；前两项不能单独算真实业务闭环完成。MVP 不承诺因果确定、普遍改善或绝无退化。完成情况、诚实报告、额外打断、耗时和成本分别记录，不能靠拒绝所有任务获得好成绩。

### 2.1 学习来源与实验边界（D-061）

学习同时覆盖失败、成功但绕路、值得复用的成功做法。成功模式只是待验证经验，不把共同出现当因果；调用少也不必然更好。效果、费用、耗时分别记录，候选前确定主目标与另两项容忍范围，不先发明统一总分。

只要求批准业务范围内的新任务有支持证据，不追求所有领域普遍改善；适用范围之外维持原行为。停用或删除无效旧规则也是改进，模型建议合并后须把合并产物当新候选验证。

Jev 的探索角色可从初筛扩到批量评价信号（重复、冲突、明确要求遗漏、候选比较），不负责最终采用裁决，仍未实测。评价器不能改自己的验收标准，错误与不确定性须可审查。

Skill 委派给子 Agent、可恢复地省略上下文都是候选实验，不是第一期必建架构。不强制一个 Skill 一个 Agent；暂不发送内容不等于删除原始证据。若选择上下文删减实验，用户约束、权限和未完成事项不得仅凭相关性评分丢弃，需检查后续影响。专用 Agent 的经验仍按版本化材料管理，不靠无限会话积累。

第一期只打通一个由真实机会支持的改动路径，不同时建设多 Agent 平台、办公工作流、多提供方路由或本地模型微调。现有逐次外部操作批准不因讨论预授权而放宽。流程跑通与真实业务有效分别验收。

## 3. 第一期不证明什么

第一期不承诺：

- 能发现所有类型的智能体问题；
- 能完全自动判断根本原因；
- 能恢复所有真实工作环境；
- 能为所有任务设计统一评分；
- 能持续产生多个有效改进；
- 能无人批准地正式启用插件；
- 能安全修改 DeepSeek Harness 核心源码；
- 能自动处理多个插件之间的复杂冲突；
- 能成为面向外部团队的完整产品。

这些内容分别属于后续阶段，不能成为第一期开工条件。

## 4. 使用者与系统角色

第一期只有三个角色，不建设复杂权限体系。

### 4.1 普通使用者

正常使用 PTC 模式完成代码任务。任务结束后尽量提供：

```text
成功 / 部分成功 / 失败
可选的一句话说明
```

普通使用者不需要选择试用任务、理解候选版本、重复执行工作或配合研究流程。

### 4.2 项目操作者

第一期通常就是项目负责人。负责：

- 确认或拒绝问题卡片；
- 修正事实错误和测试技术错误；
- 查看候选代码、权限和测试结果；
- 批准正式启用；
- 对行为退化决定继续观察、暂停或恢复旧版本。

### 4.3 自进化系统

负责：

- 自动采集真实任务事实；
- 初期在人工触发后分析新增经验，验证真实发现能力后再补空闲期自动分析；
- 主动提出重复 Harness 问题；
- 冻结验证计划和可用独立材料，整理真实关键步骤对照；
- 选择并生成最小改动，需要插件时才使用 Creator；
- 在独立测试进程中比较新旧版本；
- 保存证据、候选、失败和版本历史；
- 执行明确技术故障的自动恢复。

## 5. 用户实际看到什么

第一期只支持 DeepSeek Harness 官方网页界面，并通过本项目提供的启动命令运行。不做独立管理页面，但必须提供以下可见入口。

### 5.1 常驻状态标记

自进化功能开启后，状态标记始终可见，至少包含：

| 状态 | 用户看到的文字 | 显示要求 |
|---|---|---|
| 正常采集 | 自进化：记录中 | 低干扰但始终可见 |
| 后台分析 | 自进化：正在分析 | 更醒目 |
| 候选测试 | 自进化：正在测试候选 | 更醒目 |
| 等待操作 | 自进化：等待你确认 | 明显提醒 |
| 正式观察 | 自进化：新版本观察中 | 始终可见 |
| 暂停或错误 | 自进化：已暂停 | 明显警告并说明原因 |

状态必须同时使用文字和视觉变化，不能只靠颜色表达。状态来源必须是真实后台状态。

### 5.2 任务结果标记

任务结束后提供最小操作：

- 成功；
- 部分成功；
- 失败；
- 可选补充一句说明。

第一期可以通过现有对话卡片、消息动作或简单命令提供，不建设表单系统。

### 5.3 问题卡片

系统发现重复现象后，向项目操作者展示一张问题卡片：

- 发生了什么；
- 支持它的独立任务数量；
- 关键证据位置；
- 是否存在相反案例；
- 为什么可能属于 Harness；
- 当前是否有条件制作测试；
- 系统对修改位置的建议及不确定性。

最小操作只有：

- 确认进入测试；
- 证据不足，继续观察；
- 拒绝，不属于 Harness。

### 5.4 候选审查卡片

候选完成适用离线检查后展示（必须区分局部证据与真实使用证据）：

- 它解决的问题；
- 新增了什么 Harness 能力；
- 使用了哪些 Cordis 服务、事件、工具或界面位置；
- 需要哪些权限；
- 候选代码差异；
- 适用检查、局部对照结果、证据缺口与试用范围/期限；
- 已知风险；
- 失败时恢复到哪个版本。

最小操作只有批准和拒绝。

## 6. 完整产品流程

### 6.1 正常使用与经验采集

1. 使用者用固定 DeepSeek-V4-Flash 和 PTC 模式执行真实代码任务；
2. 系统记录任务版本、提示内容、工具调用、工具结果、运行错误和结束原因；
3. 使用者尽量标记任务结果；
4. 采集失败不能影响正常任务；
5. 真实任务、人工练习和内部分析/生成/评估从入口开始分开标记；后两类不进入真实样本统计。

### 6.2 发现重复问题与适配机会

分析入口按以下顺序交付：

- 初期由项目操作者点击或通过现有界面命令触发；
- 真实发现能力验证后，再补累积新经验且运行环境空闲时的自动触发。

没有新经验时不重复分析。自动分析只做到生成问题卡片，不自动生成或运行候选。

普通代码整理事实，大模型比较真实片段、用户纠正和成功案例，提出共同机制及反例。分类是待验证判断，不是 grep 报错即下结论；也不要求先证明“是 Harness 的锅”。Jev 可试作初筛，详见第 10 节。

默认需要至少三个独立真实任务支持同一问题。同一件工作即使跨轮次或会话重试，也只算一个支持案例；不能直接按会话数或结束事件数计数。三十个真实任务是正式复盘点，不是第一次分析的门槛。

### 6.3 人工确认问题

项目操作者可以：

- 删除错误证据；
- 补充真实任务结果；
- 删除敏感内容；
- 指出问题不属于 Harness；
- 要求继续观察。

如果人先指出问题，或直接提供根因、修改位置、关键解决逻辑，改进仍可按相同标准验证、批准和使用，但标为“人指出问题后的改进”，不能计入自主发现成果。人仅点击“开始分析”不影响自主发现资格。

### 6.4 先确定证据与验证办法

候选生成前冻结：改进假设、适用范围、目标指标、不可退化条件、检查材料、预算、观察期限和停止条件。正确依据来自真实记录、用户确认要求或已验收产物；模型可以整理检查脚本，不能同时编造标准并宣布自己成功。人工修改标准须留痕并重新建立对照。

第一期优先“真实关键步骤对照＋有限真实试用”。例如上下文压缩改进，保存真实压缩前输入及当时已确认约束，让新旧方法处理相同材料，比较信息遗漏、事实失真和成本。不要求恢复整个工作环境。

只保存经授权的必要片段、配置版本和数据引用；缺少关键输入则标记不可对照。候选不得看到未来答案。新方法改变后续工具请求时，旧轨迹的工具返回不能冒充新请求的结果；对照止于可比较步骤。小仓库、模型编题和固定回放只作工程或辅助证据，不能单独证明业务改善。

有可重建真实任务时可以做完整重跑，但不是所有改进的前置条件。已有独立材料须在候选修改前冻结并隔离；诊断暴露后转公开回归，下一版使用新冻结材料或等待新真实任务。不得挑选有利案例、换题抹掉失败或重置三版上限。

### 6.5 生成最小改动

在独立工作进程组织候选生成，先选择 Memory、Skill、配置、上下文/检索策略或插件中足够解决问题的最小改动。不是每次都创建插件，也不把所有问题塞进 Skill。

一个候选解决一个明确问题，保留来源、适用与不适用范围、前后差异、版本和撤销方式。Memory/Skill 在受管理副本中修改，不直接覆盖用户原件。涉及执行机制时，Flash Creator 查询真实 Cordis 接口，生成标准插件 bundle，只安装到独立 DSH_HOME / 测试 profile；涉及界面时检查实际渲染。

同一问题最多三个串行候选版本，影响行为的内部修改也计入。每次尝试启动前设置时间与消耗上限，覆盖准备、生成、修复和验证；先到上限即停止，保留记录并等待人工决定，不自动另开一版。真实任务执行模型与新旧对照保持固定；候选不能修改模型、安全规则或评判逻辑。

### 6.6 分层证据与隔离检查

1. **运行检查通过**：插件检查加载、停用、重启和清理；Memory/Skill/配置检查能否正确加载、作用域、冲突及恢复。都检查权限与副作用。说明可以运行，不说明业务有效。
2. **局部对照支持**：按冻结计划比较真实关键步骤，检查改善目标以及相关反例、正常材料。按影响面选择回归，不统一要求每个改动跑 5～10 个完整任务；没有独立材料时明确标记尚无独立证据。
3. **后续真实使用支持**：通过批准的有限试用收集真实结果，报告样本数、负面案例、人工纠正、耗时和成本；小样本不能声称普遍有效或零退化。

代码、生命周期和权限等可检查要求不能因观察试用而省略。确定性步骤可固定回放；模型输出不稳定时在预算内重复对照，结果矛盾就记为证据不足，不挑最好一次。模型评价仅作辅助，主观业务效果需要使用者确认。

最终产物先冻结，在干净实例按已选计划复验所有适用的离线检查，验证发布作用域；不能用开发中某次通过替代最终结果。这里的“全部适用检查”不等于强制完整历史任务重放。

### 6.7 批准有限试用，再决定保留

审查卡片列出已知收益、证据等级、缺失证据、适用任务、试用期限/任务数、预算和停止条件。操作者批准的是限定范围试用，不是全局证明成功。

一次只试一个改动；按提前确定的条件纳入随后自然发生的新任务，不让用户反复做题，也不事后挑成功任务。任务足够多时可公平分配新旧版本；第一期不建通用 A/B 平台。没有对照或样本很少时，结果只标为使用观察，不能归因于改动本身。

代码或配置只读对照不能涵盖实际副作用。重复执行会写入外部系统的操作不做双跑；不能隔离、观察或撤回的改动，第一期留在建议阶段。不可撤销外部操作仍逐次批准。

冻结的改动、模型与配置版本、证据及批准记录绑定保存。Memory/Skill 也按版本发布；已有会话保持原版本，不能因热发现而悄悄切换。插件沿用已验证的 preset 或新实例发布路径，不用主 profile 热安装冒充会话隔离。

试用到期停止扩展并交人复盘：保留、继续有限观察、修改或恢复。保留只表示当前范围和证据支持采用；扩大范围另行确认。没有遇到相关任务不算通过，不自动转为稳定。

### 6.8 自然观察与恢复

按第 6.7 节经批准限定范围试用，用户继续正常工作；只让符合条件的新会话采用候选，其余维持旧版。

- 明确技术故障：先暂停受影响任务并停止坏插件作用，再恢复上一个版本，提示用户决定如何继续；
- 行为结果变差：记录、提醒，由人决定；
- 没有出现相关任务：只记录后续证据尚未增加；
- 再次出现原问题：关联到原问题卡片，不自动删除历史结论。

恢复不能只修改之后新任务使用的清单。已挂载坏插件的任务必须暂停；无法安全卸载时停止受影响实例并用旧集合重启。整个进程因新插件故障退出时，由外部启动器处理，不能依赖已退出的控制插件。恢复后不自动重放中断操作。

新版网页能够启动不代表每个插件都正常，健康检查须核对受管理插件是否实际激活；不能在插件加载失败时仅因页面可访问就显示正常。

文件处理单独判断：自动撤销能明确归属于故障插件、且之后未被用户或其他任务修改的文件变更。归属不清、有后续改动、缺少恢复材料或无法排除并发写入的文件，保留现场并交给用户；不尝试自动合并式撤销，不恢复整个工作区。报告已撤销、跳过及失败项。最小恢复材料仍受项目授权约束，不默认保存完整代码快照。

发消息、提交外部数据等不可撤销操作不会随插件恢复而消失，第一版必须逐次取得用户批准，不能以插件启用批准代替。

## 11. 权限边界

第一期的隔离目标是防止候选误伤真实任务，不是抵御恶意代码。独立进程不构成完整安全边界；新版安装后的 Host 插件在宿主进程运行，不受工作区沙箱限制，候选按受监督的实验代码处理。Plugin Manager 的操作批准和依赖构建脚本批准遵循官方流程，不能代替正式发布批准与运行时副作用限制。

| 行为 | 隔离测试环境 | 正式运行环境 |
|---|---|---|
| 读取测试工作区 | 允许 | 按项目授权 |
| 修改临时文件 | 允许 | 必须走现有工具与批准流程 |
| 执行测试命令 | 允许 | 只读或低风险命令受限开放，其余走批准流程 |
| 访问网络 | 默认禁止 | 必须走现有工具与批准流程 |
| 不可撤销的外部操作 | 使用替身或可丢弃目标 | 每次单独批准，插件启用批准不覆盖未来操作 |
| 读取生产密钥 | 禁止 | 禁止候选直接读取 |
| 修改安全和权限 | 禁止 | 禁止 |
| 修改模型和评判规则 | 禁止 | 禁止 |
| 修改 DeepSeek Harness 核心源码 | 禁止 | 禁止 |

正式插件不能借助后台事件监听绕过原有批准流程。

测试进程只接收允许清单中的环境变量，不继承生产密钥。不需要的能力不挂载；无法可靠禁止的系统能力必须如实标明。

按 D-051，分析与测试编排在独立工作进程执行，用户仍从现有网页触发和查看状态，不增加必须学习的新命令行。

## 12. 数据与隐私

- 原始会话日志保存在本地；
- 自进化系统只保存派生摘要、证据位置、测试、候选和版本；
- 分析只向同一模型服务发送当前问题所需的最小片段；
- 密钥、环境变量值和明显敏感字段不得进入分析材料；
- Git 只保存代码、脱敏测试定义和版本清单；原始日志、完整模型请求/响应及敏感诊断留在 Git 之外，默认不保存完整工作目录；
- 新版启用前关闭并验证 `session-log-deepseek` 附带日志上传；正常模型调用仍发送必要任务上下文，不能宣称完全不外发；
- 默认保留派生研究材料和失败候选至第一期结束，用户删除请求优先；
- 接近磁盘上限时提醒人工，不静默删除；
- 用户可以删除指定任务的派生材料。

### 里程碑一：最小采集与真实发现试验

交付：

- 独立扩展项目能够加载；
- 状态标记始终可见；
- 真实任务、人工练习和内部研究分开，同一工作重试归并；
- 会话记录增量读取；
- 任务结果标记；
- 采集失败不影响正常任务。

上述最小能力具备后立即用真实记录人工触发分析，由系统提出问题和证据，保留结构化结果及人工干预记录。此时不等待完整账本、问题审批界面、自动定时分析或完整人工练习闭环。问题至少三个独立真实任务支持的门槛不变；证据不足如实记录。

通过标准：采集不影响普通任务；真实发现试验已有可审查记录，系统自行提出的问题是否有意义由操作者确认。没有合格问题时先继续收集或调整发现方法，不用扩建外围功能替代；不把“跑过分析”当作自主发现成功。

### 里程碑二：人工练习闭环

交付：

- 一个固定人工练习题；
- 重复问题卡片；
- 人工确认和修改留痕；
- 冻结验证计划和可用独立材料；
- 新旧对照记录及其能支持的结论。

通过标准：人工练习可以稳定走到“等待生成候选”，并且不会混入真实研究统计。

### 里程碑三：候选生成与隔离验证

交付：

- 生成最小改动；插件类型使用 Creator；
- 独立测试进程和可丢弃工作区；
- 最多三个串行版本，每次有时间和消耗上限；
- 真实关键步骤对照与相关回归；可完整重跑时补充完整任务证据；
- 候选审查卡片。

通过标准：人工练习题中旧版失败、新版通过，且候选失败不会影响主进程。

### 里程碑四：持久保存与恢复

交付：

- 实际候选产物冻结并在干净实例通过全部适用离线检查；
- 当前启用插件清单；
- 新版本只用于新会话；
- 常驻“观察中”状态；
- 明确技术故障自动恢复；
- 重启恢复与故障演练。

通过标准：受管理改动跨重启存在；加载及明确运行故障能暂停受影响任务并恢复；自动文件撤销不覆盖后续正常改动，归属不明或无法安全撤销时交给用户。

### 里程碑五：真实研究证明

执行：

1. 使用固定 Flash 与 PTC 模式正常完成真实代码任务；
2. 累积 30 个带结果标记的任务后正式复盘；
3. 从至少三个独立任务中发现一个有意义问题；
4. 人工只确认事实，不提供关键解决方案；
5. 完成适用验证、批准有限试用、收集真实使用证据、人工复盘保留或恢复。

通过标准：满足本文第 2 节全部条件；有真实使用支持才能称闭环完成，工程演练不算。

在真实发现能力得到验证后，补空闲期自动分析和问题/候选操作交互。保留原有最小状态提示，不建设独立管理页面。初期人工触发不降低自主发现资格；按本版证据分层与试用流程执行，预算、批准和恢复边界不变。

## 15. 30 个任务复盘

累计 30 个有结果标记的真实代码任务后，必须检查：

- 是否出现三个独立任务支持的重复问题；
- 系统有没有只发现无意义的小错误；
- 有意义问题能否落到 Memory、Skill、配置或插件等受管理改动；
- 能否获取可信局部对照和后续真实使用证据；
- 人工参与是否已经替代系统关键工作；
- 模型调用、测试时间和磁盘成本是否可以接受。

如果没有合格问题，不自动判项目失败，也不降低标准。评审结果只能是继续收集、调整发现方法或暂停项目，并记录理由。

## 17. 主要风险与处理

| 风险 | 第一期处理 |
|---|---|
| 只发现无意义小错误 | 真实成果必须由项目负责人确认具有实际意义 |
| 人工替系统完成发现 | 记录全部人工修改，超出边界后不计入自主成果 |
| 候选针对测试写死 | 暴露的失败题转公开回归，新题在下一版修改前冻结，保留独立验收 |
| 模型随机性 | 按冻结计划在预算内重复关键对照，矛盾时判证据不足 |
| 候选靠拒绝或打断避免出错 | 基础任务同时检查正常完成、额外打断与耗时 |
| 单次尝试卡住或消耗失控 | 时间和消耗任一达上限即停止，等待人工决定 |
| 候选影响真实工作 | 开发隔离；批准后限定范围试用，承认存在残余风险并可停止恢复 |
| 开发环境可用但发布产物失效 | 候选冻结后在干净实例完成适用离线复验并跨重启验证 |
| Plugin Manager 污染现有会话 | 只在测试 profile 安装候选；正式发布另行验证会话作用域 |
| 上游升级使旧证据失真 | 新旧基线分开，日志迁移后重新提取并保留源版本引用 |
| 新插件导致程序无法启动 | 由控制插件之外的启动器恢复上一份启用清单 |
| 运行中整个进程因插件故障退出 | 外部启动器恢复，受影响任务保持中断并提示用户 |
| 自动撤销误伤正常修改 | 仅撤销归属明确且无后续改动的文件，其余交给用户 |
| 新版本行为变差 | 记录并提醒，由人判断；明确技术故障自动恢复 |
| 插件越来越多 | 第一期保持独立；真实出现开销后再按能力归属整理 |
| 项目范围膨胀 | 任何新增能力必须解决已经出现的真实瓶颈 |

## 18. 第一期结束时应当能够演示

```text
正常真实工作 → 记录与人工触发分析 → 系统提出适配机会和证据
→ 确认事实 → 冻结验证计划 → 选择并生成最小改动
```
